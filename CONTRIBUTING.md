# Contributing to RJX Patches

Thanks for helping improve RJX Patches.

## Before opening an issue
- Search open and closed issues first.
- Confirm the app's package ID and exact version.
- Explain the intended behavior and provide reproducible steps.
- Never include private account data, tokens, or other secrets in logs.

## Patch proposals
A patch proposal should include:
- Target app name, package ID, and version.
- A focused description of the behavior being changed.
- The relevant code locations or stable fingerprints and why they are suitable.
- User-facing options and defaults, if any.
- Build results and actual runtime test results, clearly distinguished.
- Known limitations and attribution for reused code.

## Pull requests
- Keep each PR focused on one app or related feature.
- Follow existing Morphe template conventions.
- Use semantic commit messages (`feat:`, `fix:`, `chore:`).
- Do not hand-edit files generated by the release workflow.
- Do not claim compatibility or tests that have not been verified.

## Scope
Do not submit patches intended to bypass paid entitlements, subscriptions, or licensing checks. Keep changes transparent, user-controlled where practical, and clearly documented.
